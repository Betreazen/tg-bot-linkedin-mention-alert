# План разработки: LinkedIn Mentions Alert Bot

**Версия:** 1.0 · **Дата:** 2026-07-24 · **Основа:** [SPEC.md](SPEC.md)

> Порядок фаз выбран так, чтобы самый большой риск (реальная форма LinkedIn API) снимался
> первым, до написания основного кода. Внутри каждой фазы — подход TDD: тест → минимальная
> реализация → рефакторинг. Целевое покрытие ≥ 80%.

---

## Принципы

- **TDD:** сначала падающий тест, потом реализация. Внешние вызовы (LinkedIn, Telegram) —
  через мок httpx.
- **Маленькие модули:** 200–400 строк, организация по домену, не по типу файла.
- **Иммутабельность и явные ошибки:** без мутаций общего состояния, ошибки обрабатываются
  явно на каждом уровне.
- **Секреты вне git:** `.env` в `.gitignore`, в репо только `.env.example`.
- **Всё время — UTC** внутри; локальная зона только при форматировании сообщений.

## Фаза 1 — Каркас проекта, конфиг, БД

## Фаза 2 — Авторизация и Token Manager

- [ ] `setup_auth.py`: обмен authorization code → токены → запись в `oauth_token`.
- [ ] `token_manager.py`: `get_valid_access_token()` — проверяет срок, при необходимости
      делает refresh, обновляет БД; отдаёт срок жизни `refresh_token` для проактивного
      алерта.
- [ ] Тесты (мок httpx): токен валиден → без запроса; истёк → refresh и запись; refresh
      провалился → исключение.
- **DoD:** логика refresh покрыта тестами на всех ветках.

## Фаза 3 — LinkedIn Client

- [ ] `linkedin_client.py`: сборка запроса (заголовки, `timeRange`, per-URN), парсинг ответа
      в список `Notification`, обработка 429 (backoff), 401/403, 5xx.
- [ ] Тесты на фикстурах из Фазы 0: корректный парсинг, пустой ответ, 429 → backoff,
      ошибочный статус.
- **DoD:** клиент разбирает реальный пример ответа; ветки ошибок покрыты.

## Фаза 4 — Dedup + Notifier

- [ ] `dedup.py`: вычисление ключа (§8.4), `is_new()` / `mark_sent()` через `INSERT OR
      IGNORE`.
- [ ] `notifier.py`: форматирование алерта (§9), `sendMessage`, ретрай/`retry_after`.
- [ ] Тесты: дубль между вызовами не проходит; формат сообщения; мок Telegram.
- **DoD:** дедуп устойчив к повтору; формат сообщений зафиксирован тестами.

## Фаза 5 — Scheduler + Health / служебные алерты

- [ ] `health.py`: инкремент/сброс `consecutive_failures`, `last_successful_poll`, триггер
      служебного и проактивного алертов.
- [ ] `scheduler.py`: один `run()` (токен → per-URN запрос → дедуп → отправка → запись →
      обновление курсора/здоровья); частичный сбой по URN не роняет остальные.
- [ ] `main.py`: цикл `while True: run(); sleep(...)`, аккуратное завершение.
- [ ] Тесты `run()`: новые упоминания шлются; дубли — нет; порог сбоев → служебный алерт;
      курсор двигается только при успехе URN.
- **DoD:** полный цикл покрыт тестами на моках; порог/проактивный алерт работают.

              Ф3 ──┼──► Ф5 ──► Ф6 ──► Ф7

## Вехи (milestones)

- **M1:** Ф0 закрыта — API-риск снят, спека уточнена.
- **M2:** Ф1–Ф4 — все компоненты по отдельности готовы и покрыты тестами.
- **M3:** Ф5 — сквозной цикл работает на моках.
- **M4:** Ф6–Ф7 — контейнер, покрытие ≥ 80%, ревью пройдено → готово к боевой авторизации.

## Риски

| Риск | Митигиция |
|---|---|
| Форма/поля API отличаются от ТЗ | Фаза 0 закрывает первой, до кода |
| Нет программных refresh tokens | Проверка в Ф0; иначе — ручная реавторизация раз в ~60 дней |
| Нет стабильного `notificationId` | Составной ключ дедупа (§8.4 SPEC) |
| Rate limit LinkedIn | Backoff, не считается в порог сбоев |
| Дрейф версии API (`LinkedIn-Version`) | Значение в конфиге, обновляется централизованно |
